# school-info-dashboard Application Flow Document

## Onboarding and Sign-In/Sign-Up
When a new user arrives, they land on the main application entry point, which presents a simple welcome screen with options to sign in or create an account. If the user clicks on the sign-up link, they are taken to a Clerk-powered registration page where they can choose to register using their email address and password. After entering their name, email, and a chosen password, the user submits the form and receives an email confirmation link. Clicking that link verifies the account and redirects them to the dashboard. If the user has an existing account, they click the sign-in link which takes them to a Clerk sign-in page. There they enter their credentials or, if supported by their organization’s Clerk setup, choose a social login option. If a user forgets their password, they click the “Forgot password” link on the sign-in page, enter their email, and receive a password reset link. After resetting the password, they return to the sign-in page to log in with their new credentials. Once authenticated, the user is redirected to the main dashboard. To sign out, they open the user menu in the header and click “Sign Out,” which clears the session and returns them to the welcome screen.

## Main Dashboard or Home Page
Upon successful login, the user lands on the dashboard home page. The layout features a persistent sidebar on the left with navigation links labeled Overview, Announcements, Classes, Students, Teachers, and Chat. At the top, a header displays the school’s logo or name on the left and the user’s avatar on the right. The main content area shows an overview section containing cards with aggregated statistics, such as total number of students, classes in session, announcements published, and teachers on staff. Each card is interactive, allowing the user to click and navigate directly to the detailed list page for that data. Throughout the dashboard, a consistent design system ensures that data tables, forms, and buttons all use the same styling provided by Tailwind CSS and the shadcn/ui component library.

## Detailed Feature Flows and Page Transitions
When the user selects Announcements in the sidebar, the application navigates to the announcements list page. This page displays a table of existing announcements with columns for title, date, and status. A “New Announcement” button in the header triggers a slide-in form panel where the user enters a title, content body, and publish date. Submitting this form calls the API endpoint at `/api/announcements` and, on success, refreshes the table and closes the panel. To edit an announcement, the user clicks an edit icon on a row, which opens the same form panel prefilled with the announcement data. After making changes, the update is sent via a PUT request to the same endpoint, and the list updates automatically. If the user opts to delete an announcement, they click a trash icon, confirm in a modal dialog, and the application sends a DELETE request. The deleted row disappears and a success toast appears.

The Classes section follows a similar pattern. Navigating to Classes shows a table with class name, instructor, schedule, and enrolment count. A “Create Class” button opens a form for entering class details such as title, schedule, and assigned teacher. On submit, the form calls `/api/classes`. Editing follows the row-click pattern and deletion triggers a confirmation and API call. Once classes exist, when viewing Students, the table lists each student’s name, email, and assigned class. A “New Student” button opens a form asking for personal details and class selection. After submitting to `/api/students`, the table refreshes. Editing a student opens the same form for updates, and deletion prompts a confirmation before calling DELETE on `/api/students/{id}`. In the Teachers area, the table shows teacher name, email, and the number of classes they lead. Adding or editing a teacher opens a form where the user can assign multiple classes via a multi-select control. Upon saving, the form calls `/api/teachers` and updates the table.

In the Chat section, the user sees a conversational interface with a message input at the bottom and a scrollable chat history above. When the user types a question and presses Send, the frontend issues a POST request to `/api/chat`. The AI service processes the query and streams back a response that appears in the chat window. This flow supports follow-up questions by preserving context.

Throughout these feature flows, navigation remains seamless: clicking any sidebar link updates the URL and content without a full page reload, thanks to Next.js App Router. Users can also use their browser’s back and forward buttons to traverse their navigation history through dashboard pages.

## Settings and Account Management
To manage personal settings, the user clicks their avatar in the header, which reveals a dropdown menu containing a Settings link. Clicking Settings takes the user to a profile page where they can update their name, email, and password. Changing these fields invokes Clerk APIs under the hood. If password updates are required, the user enters their current password and new password, then saves changes which triggers Clerk’s secure password change endpoint. Below profile fields, notification preferences can be toggled for email alerts on new announcements or schedule changes. If the application includes subscription billing, the settings page also displays the current plan, billing cycle information, and a link to manage payment methods. After saving any changes, the user sees a confirmation message and can either navigate back to the dashboard using a “Return to Dashboard” link or use the sidebar.

## Error States and Alternate Paths
When a user submits a form with invalid or missing data, client-side validation powered by Zod prevents submission and displays inline field error messages. If server-side validation fails or there is an unexpected issue, the API returns an error code, and the UI surfaces a banner at the top of the page describing the issue. If the user loses internet connectivity during an operation, unsaved changes in a form remain visible and an alert appears indicating the network issue. The user can retry the action once the connection is restored. In case an unauthenticated user attempts to access a protected route by typing a `/dashboard/*` URL directly, the Next.js middleware detects the missing session and redirects them to the sign-in page, preserving the intended destination so they return after login. If the user navigates to an undefined URL, a custom 404 page informs them that the page cannot be found and offers a link back to the dashboard or home.

## Conclusion and Overall App Journey
A typical administrator’s journey begins with account creation and verification via Clerk, followed by signing in to reach the dashboard overview. From there, they explore aggregate statistics and choose a section—Announcements, Classes, Students, or Teachers—to perform CRUD operations in consistent list-and-form interfaces. The chat feature supports natural language assistance by interacting with the AI endpoint. At any point, users update their profile or notification settings through the Settings page and return seamlessly to data management tasks. Throughout the experience, robust validation, real-time feedback, and clear error handling ensure that administrators can maintain accurate school information with confidence and efficiency.
